# Karpathy 的四条编码纪律

> 来源：[multica-ai/andrej-karpathy-skills](https://github.com/multica-ai/andrej-karpathy-skills) —— 社区根据 Andrej Karpathy 对 LLM coding 常见毛病的公开观察整理，**不是 Karpathy 官方发布的 skill**，别误传。
> 原文是一份英文 `CLAUDE.md`（外加同名 skill 与示例集）。这里改写成中文，并替换成本库语境下的判据和例子。

## 什么时候该翻出这条

- 让 AI 修按钮，它把整个组件重构了
- 修一个 bug，顺手加了三个抽象层
- 它说"做完了"，但你说不清怎么验证
- diff 里混着一堆"顺手"的格式改动，review 时看不出哪行才是真正修的

## 规则原文（复制即用）

整段粘进项目的 `CLAUDE.md`（Claude Code）或 `AGENTS.md`（Codex），不需要改：

```markdown
## 编码纪律（四条）

### 1. 先想再写
不要假设，不要把困惑藏起来，把取舍摆到台面上。
- 明确说出你的假设；不确定就问。
- 有多种理解时，列出来让我选，不要默默挑一个。
- 有更简单的做法就直说，该反对时反对。
- 有不清楚的地方就停下来，指出来，问。

### 2. 简单优先
用最少的代码解决问题，不写任何投机的部分。
- 不做需求之外的功能。
- 不为一次性代码造抽象。
- 不加没被要求的"灵活性"和"可配置性"。
- 不为不可能发生的场景写错误处理。
- 写了 200 行而 50 行能解决，就重写。
自检：一位资深工程师看到这段会觉得过度复杂吗？会，就简化。

### 3. 外科手术式改动
只碰必须碰的，只清理自己弄乱的部分。
- 不"顺手改进"相邻的代码、注释、格式。
- 不重构没坏的东西。
- 匹配既有风格，哪怕你更喜欢另一种写法。
- 看到无关的死代码，说出来，不要删。
- 你的改动导致某些 import/变量/函数失去引用，可以删；原本就存在的不许动。
判据：每一行改动都能直接追溯到这次的需求。

### 4. 目标驱动执行
先定义成功标准，再循环直到验证通过。
- "加校验" → "先为非法输入写测试，再让它通过"
- "修 bug" → "先写能复现的测试，再让它通过"
- "重构 X" → "保证重构前后测试都通过"
多步任务先给简短计划，每步带验证方式：
1. [步骤] → 验证：[怎么确认]
2. [步骤] → 验证：[怎么确认]
成功标准越强，你越能自己往下跑；标准越弱（"让它能跑"），越要反复回来问我。
```

## 逐条说清楚

### 1. 先想再写

AI 最容易犯的错不是写错代码，是**看到需求就立刻开始写**——把最后一次提到的细节当主线，把真正在意的约束漏掉。

判据：动手前能不能用一句话说清「改什么、不改什么、怎么验证」。说不清就该问。

> 例：用户说「这个接口太慢了，加个缓存」。按这条应该先问：慢在哪——P50 还是尾延迟？读多还是写多？数据一致性要求如何？如果只是某个 SQL 缺索引，加缓存就是把问题藏起来。

### 2. 简单优先

原文给的例子很典型。需求是「加一个算折扣的函数」：

```python
# ❌ 一上来就是 Strategy + Config + Calculator 五件套
class DiscountStrategy(ABC): ...
class PercentageDiscount(DiscountStrategy): ...
class FixedDiscount(DiscountStrategy): ...
@dataclass
class DiscountConfig: ...
class DiscountCalculator: ...

# ✅ 先写今天需要的
def calculate_discount(amount: float, percent: float) -> float:
    """percent 取 0-100。"""
    return amount * (percent / 100)
```

原文的 Key Insight 说得准：**这些"过度复杂"的例子并不明显是错的，它们符合设计模式和最佳实践。问题在时机**——在需要之前就把复杂度加了进去，结果更难读、更容易出 bug、更慢、更难测。等真的要第二种折扣类型时再重构，成本一样低。

### 3. 外科手术式改动

这条直接决定 review 成本。让 AI 修一个空指针，它给你顺带调了引号风格、补了类型标注、重排了 import——功能性改动可能只有两行，剩下的全是噪声。

判据：**每一行改动都能直接追溯到这次的需求**。追不到，就是越界。

配套的边界感：自己弄出来的孤儿代码可以清，原本就有的死代码只能说不能动。这条和本库 [convergence-review](convergence-review.md) 是一体两面——那条管"改完之后把探索痕迹收干净"，这条管"改的过程中别乱伸手"。

### 4. 目标驱动执行

把任务翻译成可验证的目标，AI 才可能闭环。

| 弱标准 | 强标准 |
|---|---|
| 「加个校验」 | 「为非法输入写 3 个测试，跑通」 |
| 「修这个 bug」 | 「先写复现测试（跑 10 次稳定失败），修完稳定通过」 |
| 「优化一下」 | 「基准脚本跑 100 次，P95 从 800ms 降到 300ms 以下」 |

多步任务给计划时，每一步都带验证方式，而不是只列动作。这样中途某步失败，能立刻停在原地，不会带着错误往下跑。

## 取舍：它明确偏向保守

原文自己写了 tradeoff——**这些规则拿速度换确定性**，遇到琐碎任务要自行判断。

所以别把它当铁律用歪了：

- 用户明确要求「重构 / 迁移 / 大改」时，第 3 条不适用
- 一句话就能说清的琐碎改动，不必先来一轮澄清
- 它对**简单优先**的坚持有时会和"这个项目本来就该有分层"冲突，遇到有既有架构的项目，以项目约定优先

## 怎么判断它生效了

原文给的三个信号，可以直接拿来验收：

- diff 里无关改动变少
- 因为过度设计而返工的次数变少
- 澄清问题出现在动手**之前**，而不是踩坑之后
