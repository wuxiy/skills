# AI 产品走查：让 Agent 主动验收你的产品

> 来源：[向阳乔木 @vista8](https://x.com/vista8/status/2119574943021371755)（2026-11-08）。原文场景：**工具开发完了，不知道如何继续打磨优化** —— 想到大厂都有产品、设计走查验收环节，于是把这个环节写成了 AI 走查提示词，实测效果很好。

## 解决什么问题

产品"能用"之后、还说不上"好"之前的这段真空期：改哪都行、改哪又都不确定，人肉走查一个个页面又太贵。这段提示词把**打磨**从开放问题变成有角色、有维度、有分级处置的流程。

## 走查提示词（复制即用）

```markdown
你是产品经理、UX 研究员与顶级 UI 设计师的集合体。现在主动走查产品的
每一个页面与交互细节：无需等待指令，自行决定走查顺序与优先级。

从六个维度同步审视：信息架构、用户流程、操作效率、反馈机制、视觉层级、
组件一致性。每看一处，先截图留证，再对照维度判断。

发现问题立即评估严重程度：
- 高优先级（阻断使用 / 造成损失 / 明显伤害体验）→ 交给子 Agent 修复，
  修复只限该问题本身，不顺手重构。
- 其余 → 整理成可执行方案：位置 + 问题 + 证据截图 + 建议 + 严重度。

以真实用户的认知负担与情绪体验为最终标准。
目标是行业顶级，不是"能用就行"。
```

最后一句是整个提示词的锚点，**不要删**。AI 的默认验收基线是"功能能用"，不显式抬标准，它走查完只会给你一句"整体不错，建议继续观察"。

## 六个维度分别查什么

| 维度 | 查什么 | 典型问题 |
|---|---|---|
| 信息架构 | 内容分几层、入口找不找得到、同一东西各处命名是否一致 | 同一个功能两个入口叫两个名字 |
| 用户流程 | 从目标到完成要几步、哪里断、哪里走回头路 | onboarding 三步断两次，用户中途不知道下一步在哪 |
| 操作效率 | 高频操作的点击数、批量场景有没有、有没有快捷路径 | 只能逐条删除，没有全选 |
| 反馈机制 | 每次操作后系统有没有回应：loading / 成功 / 失败 / 空态 | 提交后无任何提示，用户连点三次造成重复提交 |
| 视觉层级 | 页面上最重要的东西是不是一眼可见 | 主按钮和次要按钮长得一样重要 |
| 组件一致性 | 同类控件是否长得一样，间距 / 圆角 / 色板是否统一 | 三个页面出现三种按钮样式 |

## 两个关键机制

### 1. 截图走查，不是对着代码想象

原文的执行方式：**AI 挨个功能截图**，看真实渲染效果（onboarding、功能操作 UX……）。走查必须基于真实界面证据 —— 对着代码想象 UI，等于用想象审想象。和你仓库里 [agent-browser](../experience/codex-skills-trio.md)（写完自验网页）、[playwright-scripted-testing](playwright-scripted-testing.md)（写脚本别手点）是同一个原则。前提是给 Agent 一个能跑起来的环境（本地起服务 + 测试账号），见 [best-practices 第 10 条](../experience/best-practices.md)。

### 2. 审修分流，高危才动手

- **高优先级 → 子 Agent 修复**：但修复必须外科手术式，只改这个问题本身（见 [karpathy-guidelines](karpathy-guidelines.md) 第 3 条），否则走查会演变成一场大重构
- **其余 → 只出方案不动手**：位置 + 问题 + 证据 + 建议 + 严重度，攒成清单等你排期

这个分流和 [`w-review`](../../skills/w-review/SKILL.md)（只审不改，每条带证据，严重度分级）是同构的 —— 那套纪律用在 UX 走查上同样成立。

## 什么时候用 / 什么时候别用

**用**：功能主体已完成，进入打磨期；上线前想系统性过一遍体验；换了新设计稿想验收还原度。

**别用**：核心功能还没跑通时 —— 那时候的问题走查查不出来，是需求问题不是体验问题；以及没有可运行环境时，截图走查无从谈起。
