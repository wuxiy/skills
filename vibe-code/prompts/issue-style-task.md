# 把任务写得像 GitHub Issue：目标 + 范围 + 参考 + 限制 + 验收

OpenAI 内部总结 Codex 使用经验时给出的具体方法：**把给 Codex 的任务写得像一条 GitHub Issue**。与其堆砌长篇"超级提示词"，不如给出文件路径、组件名、参考实现、diff、文档片段这些**具体上下文**——它们能让 Codex 更稳定地执行任务。

## 反面例子 vs 正面例子

**别这样写**（太模糊，Codex 只能自由发挥）：

> 帮我优化这个网站。

**要这样写**（给足边界与参照，Codex 按图施工）：

> **目标**：提高首页移动端加载速度
> **范围**：/src/home
> **问题**：首屏图片加载过慢
> **参考**：/src/product 已经实现懒加载
> **要求**：按 product 模块相同方式实现
> **禁止**：不修改其他页面
> **验收**：修改后运行相关测试并检查首页

## 核心模板

> **目标**：这次要达成什么结果
> **范围**：改哪里（文件路径 / 模块）
> **问题**：现在具体哪里不对
> **参考**：有没有可参照的现有实现 / 片段
> **要求**：按什么方式做
> **禁止**：哪些不能动
> **验收**：改完怎么证明它有效（跑哪些测试 / 检查什么）

## 关键要点

- **具体胜过详细**：五个明确字段，往往比一篇 1000 字"超级提示词"更有效。
- **给参照实现**：`/src/product 已实现懒加载` 这类参考，比口头描述"要懒加载"可靠得多——让 Codex 模仿既有写法，而不是发明新方案。
- **划清禁止边界**：`不修改其他页面` 能防止改动蔓延到无关模块。
- **验收要可执行**：写明"运行相关测试并检查首页"，给 Codex 一个可验证的完成标准，而不是含糊的"做好一点"。
