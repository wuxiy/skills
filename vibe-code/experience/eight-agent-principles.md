# Skill 将死，方法论永生 —— 给 Agent 的 8 个思维原则

> 来源：卡比老师 @jakevin7 在 B 站 Build in Public 活动的分享（记录整理）。"干中之干"，每个点都可以直接加进日常 Prompt。
>
> **暴论理解**：随着模型训练进步，很多通用知识和标准流程正被模型内化——以前要 1000 多行通用说明教它做的事，未来两三行精炼提示就能调动已有能力。**Skill 不只是文本**（还有视觉参考、工具调用等，仍有存在必要），但那些重复讲通用知识的长篇说明会越来越没用。我们应该把精力放在：**这次解决什么问题、用什么方法、怎么判断真的做对了**。

---

## 8 个原则（每个都附可直接粘贴的 Prompt 表达）

### 1️⃣ 第一性原理 —— 先把问题本身搞清楚

让 Agent 回归事实，不急着动手：

> 先回归事实：问题能否复现、根因是什么、修复前后的结果有什么变化。保证最开始的问题存在且可执行。

卡比老师用 Claude 攻克费马大定理的时事举例：100 轮对话之后，怎么让 Claude 还记得最初的任务是什么——先钉死问题，才有后面的一切。

### 2️⃣ 对抗式审查 —— 找一个专门挑毛病的 Agent

让**没有参与实现**的独立 Agent 审查，寻找反例、遗漏和失败场景，并要求它给出证据。

> 让没参与实现的独立 Agent 审查实现：找反例、遗漏、失败场景，每条意见必须给证据。

本质是多 Agent 交叉验证——让多方认可同一个结果，而不是实现者自说自话。

### 3️⃣ 消融实验 —— 拿掉一个东西，看看还行不行

论文里不可缺的 Ablation Study。某条规则、某个工具、某段提示词到底有没有用？

> 在其它条件尽量不变时，删掉这条规则/工具/提示词再跑一遍，对比结果，证明每个元素都有自己的作用。

### 4️⃣ 奥卡姆剃刀 —— 先做最简单、能工作的版本

能用一个脚本解决的事，先把脚本跑通；架构随真实需求不断迭代。呼应 Build in Public：有一个 idea 能 work，就拿去给大家审，真实反馈会塑造更好的产品。

> 先做最简单能工作的版本，不要预建框架；架构随真实需求演进。

### 5️⃣ 列出所有不自信的点 —— 让不确定有地方出现

明确要求 Agent 交代：哪些结论缺少证据、哪些场景还没测、哪些地方只是猜测。Agent 再强也会犯错，只有自查才能降概率。

> 列出你所有不自信的点：哪些结论缺证据、哪些场景没测、哪些只是猜测。

### 6️⃣ 保持独立思考 —— 先判断，再参考别人的答案

多 Agent 协作时，让每个 Agent **先独立给出结论和依据，再互相讨论**——更容易发现分歧，避免一个说错、其他跟着点头。后面还展开讲了多 Agent 架构怎么选（Swarm / Graph / Agent Team 等）。

> 先各自独立给出结论和依据，再互相讨论；不要直接参考别人的答案。

### 7️⃣ 批判性思维 —— 必须检查证据

不要因为一段分析讲得完整就默认它成立。让 Agent 区分**观察到的事实**与**推测**，并说明**什么证据会推翻自己的判断**。

> 区分事实与推测；说明什么证据出现会推翻你的判断。

### 8️⃣ 高内聚、低耦合 —— 把模块边界划清楚

相关逻辑放一起，不同模块通过清晰接口协作。这直接影响 Agent 的工作难度：改一个模块要理解的范围越明确，越容易给它合适的上下文，也越方便验证。

> 相关逻辑放一起，模块间用清晰接口协作；改一个模块时受影响范围要明确。
