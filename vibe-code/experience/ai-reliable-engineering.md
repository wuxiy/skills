# AI 可靠系统工程三环：目标对齐 / 路径探索 / 循迹前行

> 来源：Erwin @ErwinWu000，由资深程序员卡颂（@kasong2048）启发——「AI 审代码挑出的问题往往不是编码失误，而是需求没对齐导致 AI 只能脑补」。
> 原文：https://x.com/ErwinWu000/status/2094991204375240733
>
> 核心论断：AI 编程要从"整点东西玩玩"变成"可靠的系统工程"，就三件事——**目标对齐（定义终点）、路径探索（找到路径）、循迹前行（走在正轨）**。三者是环环相扣的闭环，不是孤立技巧。

---

## 1️⃣ 目标对齐 —— 定义程序的终点

> 需求工程的核心本质是两件事：**消除隐性假设** + **建立唯一事实来源**。

### 问题
丢给 AI 的 Prompt 往往是**带着个人偏见的半成品解法**。你说"做个支持微信登录和购买会员的功能"，但业务里藏着的隐性上下文 AI 根本看不到：

- 支付超时怎么回退库存？
- 微信回调重复通知如何做幂等校验？
- 多端登录时 Token 如何刷新？

AI 只能基于训练集的概率分布**在解空间里硬猜**——做出来跟你想的不一样，又让人恼火。
Fred Brooks 早就说过：构建软件系统最困难的单一环节，就是**精确决定要构建什么**；没有哪个环节做错会对系统造成如此致命的破坏，事后也最难纠正。

### 落地实践：苏格拉底式需求获取（grill-me / grill-with-docs，来自 matt pocock/skills）
让 AI **先别急着敲代码**，先扮演严苛的架构师反过来"拷打"你：

> 并发边界是多少？第三方服务挂了怎么降级？数据冲突怎么处理？

直到把所有隐藏假设剥离干净，**自动落成一份清晰的产品和技术规格文档（Spec）**。
仓库关联：[goal-mode](prompts/goal-mode.md)（验收清单驱动开发）是同一思路的轻量版，本方法论是它的大厂完整版。

## 2️⃣ 路径探索 —— 找到通往终点的路径

需求确定后，通向目标的路径不止一条，且每条路还会分出技术分支。选路不能只看"能不能实现"，要放在当前工程的具体局限下权衡四个维度：

| 维度 | 问什么 |
|------|--------|
| 实现的复杂性 | 初始交付的技术门槛高不高？ |
| 维护的复杂性 | 未来会不会变技术债？模块耦合度多大？ |
| 时间与资源成本 | 第三方依赖贵不贵？开发周期赶不赶？ |
| 方案的可逆性 | 走不通时，调头推倒重来的代价多大？ |

### 现实：先 probe 再踩油门
选完方案也不能百分之百确定可行，必须先探索（探一下），探通了才敢继续。
通往终点的路径本质是**拓扑网络**，中间充满分支与不确定性 → 动手前必须有**宏观架构规划**：先定拓扑，再定具体实现。借鉴 **ADR（架构决策记录）**：明确写下"背景-决策-后果与代价"。

### 落地实践（来自 matt pocock/skills）
- **wayfinder**：全局拓扑规划与路径导航，把不同架构路线拆解、对比
- **research**：某分支可行性存疑时，自动触发技术探针（Spike），检索最新文档、测试第三方 API 边界
- **prototype**：借鉴《程序员修炼之道》**示踪弹（Tracer Bullets）**——用极简代码端到端打通一条核心通路，用最小系统验证方案能否闭环

## 3️⃣ 循迹前行 —— 保证自己不偏离轨道

### 问题："盲盒式开发"
一轮接一轮把需求抛给 AI，闭着眼连续点 Accept，完全不记录中间改动了哪些模块与底层设计——直到某天系统崩溃，你和 AI 都不知道这堆逻辑怎么长成这样的。两个失控点：

- **上下文漂移（Context Drift）**：对话轮次一多，AI 逐渐忘掉早期架构约束，拿过时旧方案乱改
- **局部测试陷阱（False Green）**：AI 写的单元测试全绿，真正拼起来整个系统跑不通

### 落地实践①：活文档与变更追溯（to-spec / to-ticket，docs-by-versions）
开发中的**每一个改动都必须有迹可循**：
- 每次方案调整（新增需求或改动已有需求），改动前先做**变更影响分析**：评估波及哪些模块和接口
- **新增需求**（不涉及改动原有系统）→ 走 to-spec、to-ticket 的常规需求开发流程
- **修改已有系统** → 先开变更单（CR），再 to-ticket，执行

### 落地实践②：最小可用 E2E 验收（BDD 思路）
纯 TDD 在 AI 编码下有硬伤：**AI 极其擅长为了让测试断言通过而硬凑代码**，写出打补丁式垃圾逻辑，牺牲结构合理性。必须结合 BDD：
- **后端 + 数据库交互** → 自动化的 **API 契约测试**
- **前端 + 交互界面** → AI 不会主动写健全的 UI 自动化，必须由**人类开发者代入真实用户**，梳理关键用户流程，写一个**覆盖完整体验流程、最小可用的端到端集成验收测试（E2E Smoke Test）**，作为交付的物理硬指标

> 与仓库的 [issue-style-task](prompts/issue-style-task.md)（验收驱动）、[execution-discipline](prompts/execution-discipline.md)（Review 门禁）互为补充：它们管单任务粒度，本方法论管全流程骨架。

## 4️⃣ 总结：三环闭环

- **定义目标（起点）**：目标没扣死、隐性假设没剥离 → 后面走得再快也是在错误方向上狂奔
- **找到路径（骨架）**：只看眼前、不探清路径网络与架构分支 → 执行时频繁撞墙、反复推倒重来
- **保证实施（护栏）**：缺乏变更追踪和端到端验收 → 对话轮次一多就是执行中悄然失控

> **一句话**：目标、路径、执行三环紧扣。把这三层工程约束建起来，AI 才能真正从"单点修修补补的玩具"变成"可以交付复杂工程的可靠生产力"。
