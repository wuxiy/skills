# Agent 友好工作流：思维快捷键 / 端到端测试环境 / Review

> 来源：黄同学h（@huangtongxueh，大厂 Agent 开发）《入职大厂两个月，我的 AI 开发心得》
> https://x.com/huangtongxueh/status/2108577165306687938 · X Article 2026-10-09
>
> 一句话：**Harness 不只是给 Agent 正确的上下文，还要给它能执行任务的环境，以及判断结果的依据。**

## 背景：重 Skill 正在变成噪声

- **Harness Engineering 兴起**：通过增加约束来更好地驾驭强模型（如 Superpowers 这类重 Skill，围绕 Spec 和 TDD 组织任务）
- **弊端**：Token 消耗快；流程僵化——"哪怕某个步骤已经没必要了（上下文已足够可以直接实现），模型仍会沿既定流程继续执行"
- 模型能力增强后，**原本有用的约束正在变成噪声**。OpenAI 发布 Astra 时专门写博客讲如何清理不必要的 Skill 和系统提示词

## 一、常用工具与 Skill

### 工具分工

| 用途 | 工具 |
|------|------|
| 编码实现 | Codex + GPT-5.6 Sol |
| 规划 | Astra（Astra 之前用 GPT-5.6 Sol Max） |
| 简单需求 | pi + DeepSeek V4 Flash |
| 对抗性审查 / Code Review | Claude 5 Fable |
| 个人项目方案设计 | 网页端 GPT-6 Pro |

### 常用 Skill

| Skill | 用途 |
|-------|------|
| `think`（tw93） | 方案对齐、头脑风暴 |
| `grill me` / `grill with docs` | 需求澄清：连续追问把目标/约束/取舍问清，沉淀到 ADR 或 `CONTEXT.md` |
| `implement`（Matt Pocock） | 配合 grill，实现已明确的计划或 Issue |
| `ponytail` | 清理 AI 的过度设计、降低 Review 难度（**常因 GPT-5.6 Sol 过度设计**） |
| `handoff` | 把上下文整理成文件，跨会话/跨 Agent 交接（Codex → Claude Code / pi） |
| `check` | 代码审查，提 MR 时用 |
| 自沉淀 SOP | 端到端测试等可复用流程 |

> **判断标准**：日常工作中，**一个流程重复超过三次，就可以让 Codex 帮你整理成 Skill**，之后直接复用。

## 二、五个"思维快捷键"Prompt（可直接复制）

作者的核心观点：**与其给模型写死一套完整思考流程，不如用准确的方法论告诉它"应该以什么方式思考"，再补充当前任务真正必要的约束。**

这些 Prompt 之所以有效，是因为它们都是**人类知识中已高度标准化**的方法论——模型训练时见过大量相关论文与代码，不需要再手写几百行 Workflow。

### 1. 第一性原理

> 不要基于"加 Redis 缓存"这个既定方案继续设计。从第一性原理分析这个接口为什么慢，以及最小必要的解决方案。

模型关注点从"Redis 怎么设计"切换到："瓶颈到底在 SQL、网络、序列化、锁竞争，还是重复计算？如果加个索引就能解决，为什么要引入 Redis？"

**适合**：怀疑"题目本身可能就问错了"的时候。

### 2. 对抗性审查

> 对这个方案做一次对抗性审查，优先寻找能推翻核心假设的反例。

（对比普通问法："帮我看看这个技术方案有没有问题"）

方案是"为重复请求引入分布式锁"时，模型不再只谈锁超时时间，而是追问：重复请求真的需要互斥吗？接口幂等能不能解决？锁服务挂了怎么办？锁过期但业务没跑完怎么办？**是不是为解决局部问题引入了新的分布式故障点？**

**适合**：方案评审、Code Review。

### 3. 消融实验

> 给这三个优化设计消融实验，判断真正的收益来自哪里。

（前提："加索引、Redis 缓存和批量查询后，接口耗时从 800ms 降到 100ms"）

模型会设计对照组（Baseline / 只加索引 / 索引+缓存 / 三者全上），最后可能发现：**只加索引就已从 800ms 降到 120ms，剩下两个复杂方案只贡献 20ms**——那哪些复杂度可以不要，就清楚了。

### 4. 奥卡姆剃刀

> 用奥卡姆剃刀重新审查这个设计，在满足需求的前提下，删除所有非必要机制。

面对 "Kafka + Redis + 分布式锁 + 状态机 + 定时补偿" 这种设计，模型可能得出："当前场景只有单库写入，一个事务加唯一索引就够了。"

**对 Coding Agent 尤其有用——模型很容易为了"完整"而过度设计。**

### 5. 高内聚、低耦合

> 按高内聚、低耦合原则审查 OrderService 的职责边界，不要为了拆而拆。

模型会检查："为什么订单服务同时负责库存、优惠券、短信、支付和报表？哪些属于订单领域本身，哪些该通过稳定接口交给其他模块？"

**它激活的不是简单"拆文件"，而是一整套模块化、信息隐藏、依赖方向和职责划分的判断。**

### 把它们组合起来

作者现在很少写"第一步分析需求，第二步检查假设…"，而是直接给：

> 从第一性原理重新分析，对当前方案做对抗性审查；核心机制必须通过消融实验验证；方案遵循奥卡姆剃刀，代码保持高内聚、低耦合。

**这几十个字背后指定了五种认知动作**：重新定义问题 → 攻击假设 → 验证贡献 → 删除复杂度 → 整理系统边界。

## 三、日常开发工作流

1. **投喂上下文**：把 PRD、会议纪要、聊天记录、用户反馈交给 Agent（这些材料往往并不完整一致——PRD 没更新、会议补了限制、聊天调了优先级，且你自己的理解里也藏着没说的假设）
2. **grill 需求对齐**：结合团队 Wiki 和现有代码，连续追问会影响实现的目标、边界和取舍
   - **尺度控制**：当剩下的问题**已经不会显著改变实现方向和验收结果**时，就可以开始开发——不要要求把实现细节全提前规划好，否则对齐本身又变成很重的流程
3. **沉淀 Spec / `CONTEXT.md`**：记录这次要解决的问题、范围、关键决策、验收标准（供实现和审查的 Agent 共享同一份上下文，不必重读全部对话）
4. **按复杂度决定执行**：简单需求直接实现；复杂需求拆成**边界清楚、可独立验收**的 Issue。**只有能独立推进的部分**才交给 subagent 在不同 worktree 并行，主 Agent 负责集成
5. **编码 Agent 先完成测试** → 按复杂度引入其他 Agent 做**交叉对抗性审查** → 问题统一反馈给主编码 Agent（Codex）修复并重新验证
6. **人工 Review 前先跑端到端测试**。不逐行读代码，主要看**测试结果 + 核心业务逻辑**。前提是 **MR 足够小**，随开发推进逐步验证完整业务路径

## 四、构建 Agent 友好的端到端测试环境

**核心问题**：没给 Agent 端到端测试环境，它就没机会在编码和自测阶段发现问题——所以上线后仍会遇到预期之外的错误。

搭建方法就是把**你日常自测的流程提炼出来**：能工具化的做成 MCP 或 CLI，可复用的流程写成 Skill。前期费功夫，但之后显著加快开发、减少返工。

**四件事**：

1. **让 Agent 熟悉环境**：一键启动测试环境、创建测试数据，明确当前版本/测试账号/权限，提供清理与重置能力
2. **让 Agent 能操作业务系统**：通过浏览器、API 或 CLI 执行真实业务流程
3. **让 Agent 方便地查库表和日志**：只读数据库 MCP 确认落库结果，日志系统 Skill + Trace 查链路状态、定位问题
4. **把繁琐但稳定的流程复用起来**：稳定操作写成脚本，入口和排障方法整理成 Skill

**四个进一步做法**：

- **浏览器自动化**：推荐开源浏览器 `ego lite`；搭配 `pi agent + DeepSeek V4 Flash` 快速跑完测试
- **把操作统一封装成 CLI**：整合可复用 Skill、配好的 MCP、写好的脚本，提供环境检查 / 数据准备 / 场景执行 / 结果查询 / 清理——"其实也可以成为一个内部提效工具"
- **让工具直接服务于验收**（最重要的一条）：
  > DB 查询用于确认状态，日志和 Trace 用于解释失败，但**预期结果仍然必须来自业务契约，不能让 Agent 看到系统返回了什么，就认为什么是正确的**。复杂业务逻辑下，系统完全可能返回一个看似合理、实际不符合需求的结果。**工具帮助我们获取证据，而不是替我们定义正确答案。**
- **产品本身是 Agent 时，还要检查答案质量**：除了流程跑通，还要考虑 Agent Eval

## 五、Review AI 写的代码

前提：**业务需求的第一责任人仍然是开发者**——不做 Review，大型系统里很容易出问题（"你也不希望半夜被叫起来 On-call，最后发现是 AI 写的代码出了问题吧"）。

1. **先看验收标准，再看测试结果**：确认是否符合预期、有无遗漏。不能只看测试通过多少，还要看**这些测试是否验证了这次需求真正关心的事情**
2. **沿业务路径看实现，精力放在高风险部分**：重点查**权限、状态变化、并发、重试、数据一致性、迁移和回滚**；模式稳定的 CRUD 可以少看甚至不看
3. **专门检查新增的抽象和机制**：用奥卡姆剃刀思路再让 AI 审一遍——是否真有必要、有没有更简单的实现、是否为局部问题引入了过多复杂度
4. **MR 较多时构建专门的 Review Bot**：与"直接调 Agent 做对抗性审查"不同，它强调把 **Git 变更信息 + 预先设计好的审查流程**结合起来，形成可重复执行、专门服务于 MR 的审查能力

## 六、总结与思考

- **当前最大瓶颈是 Review 的速度**：Agent 能同时推进多个任务，但"我理解业务、判断方案和确认交付的速度并不会成倍增加"。只让它写得更多，结果只是**积压更多等待审查的代码**
  → 改进方向：**让重复问题在交到我手里之前就被发现和修复**。类型检查/测试/业务断言能发现的，让 Agent 自己处理；需要人判断的，集中到"需求有没有理解对、关键业务逻辑是否成立、还有哪些没验证的风险"
  → Review Bot 的价值要看**能否减少有效问题的遗漏和人工负担，不能只看它评论了多少条**
- **Harness 三要素**：正确的上下文 + 能执行任务的环境 + 判断结果的依据
- **工作流要定期做减法**：有些步骤是在弥补某代模型的短板，模型变了就该重新判断它是否还有收益。**Astra 更新后，作者就删掉了 `AGENTS.md` 里一些过于严格的约束**
- **测试和 Review 降低不确定性，但人仍需给出正确的验收标准**：
  > 即使代码和测试互相对得上，也可能是它们一起误解了需求。端到端测试覆盖的也只是选定环境和场景中的行为；生产环境里的流量、并发和数据分布，仍可能带来新问题。
- **AI 减少了亲自踩坑的机会**：原本要经历问题、排查原因才能获得的经验，现在可能变成 AI 一句"我错了，现在修改一下"——所以留出时间学习和复盘，思考 AI 时代研发真正需要的能力
