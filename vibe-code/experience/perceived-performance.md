# 前端"感知性能"：不提高后端性能的体验优化

**问题**：前端里面有哪些 tricks 在没有提高后端性能的情况下，换取体验提升的？

**核心思路**：真实延迟没变，但通过占位、预取、缓存、乐观 UI、动画等手段，把"等待"藏起来，让用户主观上觉得快、觉得连贯。

## 速览

| # | Trick | 一句话 |
|---|-------|--------|
| 1 | 骨架屏 / 渐进加载 | 先渲染框架与占位，数据到齐再填内容 |
| 2 | 预取 / 预加载 | hover 或滚进视口就提前请求下一页 |
| 3 | 客户端缓存 + SWR | 先展示旧数据，后台静默刷新 |
| 4 | Debounce / Throttle + 本地反馈 | 输入防抖，本地立刻更新 UI |
| 5 | 渐进增强的表单 | 分步表单、本地校验优先 |
| 6 | 占位排序 / "伪即时排序" | 前端先调整顺序，异步通知后端保存（乐观 UI） |
| 7 | 动画过渡与过场 | 用 layout transition / 进度条掩盖接口延迟 |
| 8 | 局部 Loading | 只锁发生变化区域，不锁整页 |
| 9 | 离线优先 / 请求排队 | 先写本地队列，网络正常再批量同步 |
| 10 | 粗粒度一致性 + 延时刷新 | 本地推断值 + 定期全量刷新覆盖 |

## 1. 骨架屏 / 渐进加载

用 Skeleton 代替空白加载，比纯 Spinner 让用户更有"已在进行中"的感觉，感知时间明显缩短。渐进加载列表：先渲染框架（导航、页头、占位卡片），数据到齐再填内容，避免"白板→瞬移完成页面"的突兀感。

典型用法：列表页、详情页、Dashboard 首屏，SSR + skeleton 占位，是非常高 ROI 的体验优化。

## 2. 预取（prefetch）与预加载（preload）

- **Hover 预取**：鼠标 hover 菜单 / 链接就开始请求下一页数据，等用户真正点击时几乎"秒开"，后端没变但平均等待时间被隐藏掉了。
- **Viewport 预取**：列表滚动时，提前请求即将进入视口的下一页数据；对无限滚动、Feed 信息流提升很明显。

可以在前端路由层 + 数据层分别做预取：路由级 prefetch（下一页面 bundle）、数据级 prefetch（下一请求数据）。

## 3. 客户端缓存 + Stale-While-Revalidate

利用 HTTP 缓存或前端状态库，把最近访问的数据当"旧数据"，立即展示，再在背后静默刷新（SWR 模式）。用户看到的是"马上有内容"，即使不是最新，刷新回来时可以平滑合并更新，感知体验比 loading 强很多。

例如：用户多次打开同一个详情页或列表，可以直接展示上次的快照，再在背景里拉最新。

## 4. Debounce / Throttle + 即时本地反馈

- **搜索框**：输入时不立刻请求，而是 debounce 300ms；同时本地立刻更新 UI（高亮关键词、展示历史搜索），减少"卡顿感"和后端压力。
- **按钮点击**：立即给出按下状态 / 波纹 / Loading 状态，而不是等接口返回再变化，让用户觉得"系统收到了"。

这一类通常配合 loading 状态和"局部占位"，避免整页阻塞。

## 5. 渐进增强的表单体验

- **分步表单**：把一个长表单拆成步骤，先本地校验、渐进提交；可以先提交轻量字段，重计算 / 风控等放在后一步，避免重操作阻塞整体验。
- **本地校验优先**：能在前端校验的都先校验（必填、格式、简单规则），减少"提交后才发现报错"的拉扯感。

用户主观上感觉"一直在向前推进"，而不是卡死在一个提交点。

## 6. 占位排序和"伪即时排序"

列表操作（比如拖拽排序、置顶、收藏）可以在前端先调整顺序，然后异步通知后端保存，实质上就是乐观 UI 的排序版本。

对一些"仅自己可见"的个性化排序，甚至可以完全在本地存储（localStorage / IndexedDB），把后端当备份源，前端体验几乎零延迟。单机 / 局部状态多的产品（个人配置、偏好面板）非常适合这样处理。

## 7. 动画过渡与过场

- **Layout Transition**：比如 React 19 的 Transition + useOptimistic、一部分框架内置 layout animation，可以把"闪跳"变成"平滑移动"。
- **路由过场**：页面切换时用淡入淡出、progress bar（类似 YouTube / Next.js 的顶部进度条）掩盖接口真实延迟。

动画不减少真实时间，但可以显著提升"控制感"和"连贯性"。

## 8. 局部 Loading 而非整页锁死

只对发生变化的区域展示 loading 或 skeleton，而不是全屏蒙层；用户可以继续操作其他区域。例如提交某个 card 的修改时，只在 card 内显示"保存中"，避免阻塞整个页面。

这类实际上是"粒度控制"，通过 UI 结构变化减弱延迟的心理负担。

## 9. 离线优先 / 请求排队

操作先写入本地队列（localStorage / IndexedDB），前端 UI 立即反映，后台网络正常时再批量同步；失败再做重试或标记。

在弱网 / 移动场景，这种"即使没网也能先操作"的感觉体验会碾压传统请求式交互。适合：消息草稿、日志记录、待办、笔记这类"允许最终一致"的业务。

## 10. 粗粒度一致性 + 延时刷新

某些全局计数（未读数、点赞数总数）不必每次强一致；前端可以使用本地推断值，定期（比如 30s）或在特定节点触发刷新即可。比如点赞后，本地直接 +1，真正的总数由下一次全量拉取覆盖。

牺牲一些强一致，换取频繁交互中的"顺手感"。
