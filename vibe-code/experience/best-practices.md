# AI 编码最佳实践：20 条规则

> 作者手写并反复调整的一套规则，覆盖从「提需求」到「复盘」的完整闭环。
> 用法分两层：**全文给人看**，理解每条背后的判断；**文末的「可粘贴版」给 Agent 看**，贴进 `AGENTS.md` / `CLAUDE.md`。

## 这套规则在解决什么

三种反复出现的损耗：

1. **把 AI 当补全工具用** —— 只敢让它写函数，不敢让它扛模块，模型能力被严重低估
2. **不放心，于是替它想细节** —— 上下文里全是你的实现假设，它反而没了判断空间，最后做出来的还是你脑子里那套半成品
3. **出问题就推翻重来** —— 没有验证脚本、没有回归集，同一个坑能踩三次

20 条按六个阶段排：需求 → 规则 → 编码 → 排查 → 审查 → 发布 → 复盘。

---

## 一、需求：把想法说满，把实现放开

### 1. 从「技术实现编程」转成「许愿式编程」

模型能力已经足够强，**大胆把想法说出来，给它足够高的要求和任务，不要预设它做不到**。

反过来说：如果你描述需求时已经开始想"这个用 Redis 缓存一下"，那说明你在替它做技术决策——把方案说成需求，它只会照着你的半成品实现，做不出更好的东西。

### 2. 多讲背景和目标，少替他考虑技术细节

告诉它**为什么要做、给谁用、做成什么样你认为最好**，具体技术细节让它自己判断。

这条和第 1 条是一体的：放手不是不管，而是把注意力从"怎么实现"挪到"为谁解决什么"。给不出背景，等于让它凭概率猜一个业务。

### 3. 优先用业界最好的模型

用差模型是双重浪费：来回几轮让你干得不痛快，时间也一起赔进去了。

省模型钱的正确方式是**缩短任务链路**（拆小、给足上下文），不是拿弱模型硬扛复杂任务。模型选型与 reasoning effort 的配置见 [codex-config](codex-config.md)。

### 4. 新功能、新配置、新开关，先问你

没有人会用的功能、开关、文案，一律不要让它加。让 Agent 每次先找你确认，慢慢把这套产品规范沉淀下来。

这条的意义不只是"少加东西"——**沉淀下来的规范本身就是下一次的输入**，规则越攒越准。

### 5. 想法可以很大，交付要拆到最小可用版本

每次只让它做**能独立跑通的最小切片**，别一次写一大坨再提交。出了问题能随时撤回，也是你能持续 review 的前提。

---

## 二、规则：让 Agent 读懂你的意图

### 6. 让 Agent 了解你的说话风格

- 你说「看看」「分析一下」——**只读代码、分析问题，不要动手改**
- 你说「修复」「修改」——才动手
- **每次提交、发布、删除，都先找你确认**

这条不写进规则里，Agent 就会把"分析问题"理解成"顺手修掉"，diff 里全是没被要求的改动。呼应 [karpathy-guidelines](../prompts/karpathy-guidelines.md) 的「外科手术式改动」。

### 7. `AGENTS.md` / `CLAUDE.md` 只写代码里看不出来的东西

除去重点的项目型要求，只写**从代码读不出来的规则**，以及**被否决过的方案**（防止它再次提出来）。写"要写清晰的代码"这类废话，只会稀释真正重要的那几条。

> **密钥和 token 不要贴给 Agent。贴了就当已经泄露，立刻去换。**
> 这不是提醒，是事故处理流程。

渐进式披露的拆法见 [refactor-agents](../prompts/refactor-agents.md)。

### 8. 必须遵守的规则，不要只信 prompt

prompt 可能拦不住，**一定要用规则脚本去限制**，让它真实跑一遍通过才算完成。

同一个错误被抓到两次，就该机械化了——写成 lint、写成 CI 检查、写成 hook。测试规则怎么落成 lint 见 [business-testing-rules](../prompts/business-testing-rules.md)。

---

## 三、编码：先对齐，再动手

### 9. 写代码前，先让 Agent 讲清楚要改哪里

说清**改动范围**和**会影响到什么功能和效果**。这一步不是为了审批，是为了**补你的上下文**——你才知道这次改动真正的风险面在哪，判断该不该做。

### 10. 让 Agent 给自己造一套验证脚本

基于项目补一个能自验的脚本，关键节点跑一遍，完成功能后检查并把结果输出给你看。逐步沉淀成这个项目的 **Agent 测试功能集**。

没有验证手段，它就只能靠"看起来对"来交付。E2E 环境怎么搭见 [agent-friendly-workflow](agent-friendly-workflow.md)，别让它手动点页面见 [playwright-scripted-testing](../prompts/playwright-scripted-testing.md)。

### 11. 多 Agent 并行：一个 Agent 一个 worktree

各自用独立的 worktree 目录，**只提交自己改的代码，不碰别人的**。全部改完合到一起，再完整跑一遍测试。

> **注意这条和 [execution-discipline](../prompts/execution-discipline.md) 的冲突**：那份文档要求「禁止 worktree、禁止分支、禁止并行」，走的是**单 Agent 串行**路线。
> 两者不矛盾，是适用场景不同：需求边界清晰、可以独立验收时用并行；需求还在探索、改同一批文件时用串行。**不要在同一任务里混用。**

---

## 四、排查：别猜，去看

### 12. 修 Bug 先找原因

**两次没修好，就停下来加日志**，看真实的数据和运行效果，别继续盲猜。

盲猜的特征是：改动越来越小、越来越随机，但没有一次能说清"为什么这样就能好"。

### 13. 三次修不好，清空上下文重来

把**问题、诉求、以及已经试过的解法**重新写清楚，让 Agent 从干净上下文重新开始。

上下文里积累了大量失败尝试后，Agent 会沿着错误假设继续推理——比从头开始更慢。这条最反直觉，但省下的时间最多。

---

## 五、审查：解耦，限轮次

### 14. 写代码的 Agent 和 Review 的 Agent 分开

保持解耦，一方不会被另一方带偏。自己审自己，等于给自己背书。

具体执行见 [`w-review`](../../skills/w-review/SKILL.md)：只审不改，每条意见必须带证据，结论落到「可以进 / 补齐后可进 / 不能进」。

### 15. Review 最多跑 3 轮

防止跑着停不下来。**第二轮开始只看新改动的地方**，不要把之前 review 过的再翻一遍。

3 轮上限也倒逼第一轮就仔细——用"慢慢试"掩盖质量问题的成本被掐死了。

### 16. 越危险的改动查得越深

删除、付费、发布这类**单向门**操作，你必须自己看一遍、点一下、确认实际效果。

单向门的意思是：做错了不能靠回滚解决。这类改动不接受"Agent 说没问题"。

---

## 六、发布：留好回滚的路

### 17. 每次提交写清三件事

**做了什么、怎么验证、出问题怎么回滚。**

git 记录本身就是 Agent 最好的上下文——下次接手的人（或 Agent）读 commit 就能恢复现场。规范见 [commit-message](../prompts/commit-message.md)。

### 18. 渐进发布：开关 + 节奏

对外的功能先在软件里加一个 **beta 更新开关**，然后按 **自己 → 尝鲜用户 → 全量** 的节奏推。不要一上来就全量。

两层意思：开关是机制（出问题能秒关），节奏是策略（让问题在小范围内暴露）。既是对用户负责，也是给自己留验证窗口。

---

## 七、复盘：把坑变成资产

### 19. 每个线上 Bug 和用户反馈，都留一个测试案例

每次上线前跑一遍。**换模型的时候也把这些旧问题全跑一遍**——这是判断新模型行不行的最直接证据。

这条把"踩过的坑"变成了可复利的资产，见 [ai-code-evolution](ai-code-evolution.md)。

### 20. 修问题要举一反三

把**同类问题一起修掉**；优化功能、完善视觉时同理，别只改一个地方就以为完事。

一个页面上的间距问题，通常意味着整个设计系统在这个维度上都没定义。见 [convergence-review](../prompts/convergence-review.md)。

## 可粘贴版（给 Agent 看）

整段贴进 `AGENTS.md`（Codex）或 `CLAUDE.md`（Claude Code）：

```markdown
## 协作规则

### 我怎么说，你怎么做
- 我说「看看 / 分析一下」——只读代码、分析问题，不要改代码。
- 我说「修复 / 修改」——才动手。
- 提交、发布、删除之前，都先问我确认。
- 新功能、新配置、新开关，先问我要不要加。没有人用的东西不要加。

### 动手之前
- 先告诉我：要改哪些地方、会影响什么功能和效果。
- 有歧义、有多种理解、有更简单的方案，直接说出来，不要默默选一个。
- 大想法拆成最小的可用切片，一次只做能独立跑通的部分。

### 动手之后
- 用项目里的验证脚本真实跑一遍，把结果给我看，不要只说"应该没问题"。
- 提交信息写清：做了什么、怎么验证、出问题怎么回滚。
- 修 Bug 要举一反三，同类问题一起修。

### 修不好怎么办
- 修 Bug 先找根因。两次没修好，停下来加日志看真实数据，不要继续猜。
- 三次还不对，我会清空上下文重开；你把问题、诉求、试过的解法重新说清楚。

### 边界
- 只改这次需求相关的代码，不顺手"改进"相邻代码。
- 越危险的改动（删除 / 付费 / 发布）查得越深，这类改动我会自己确认。
```

## 附：两个日常动作

原文档里的两条工作流，保留在这里：

- **周期性跑 `/better-harness`** —— 让 AI 基于证据（而非感觉）指出工作流里值得改进的地方
- **维护业务术语表** —— 让 Agent 马上知道你在说什么，前期成本最低的杠杆，显著减少澄清往返
