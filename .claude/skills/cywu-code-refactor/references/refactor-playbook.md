## 1. 基线与安全网

动手改代码之前，按顺序确认：

1. **基线是绿的**：跑一遍项目的测试/构建/类型检查，确认当前全部通过。基线本来就是红的？先修到绿，或明确记录哪些失败与本次无关——否则重构后无法区分"我改坏了"还是"本来就坏"。
2. **没有测试的关键行为，先补最小验证**：对即将重构的核心行为补 characterization test（描述现状的测试：输入 X 得到 Y，不评判对错只锁定行为）。补测试的成本远低于事后排查"重构到底改了没有"。
3. **行为变更清单**：重构默认不改行为。如果某项修改必然改变行为（如修掉一个确认的 bug），把它从重构计划中单列，标注"行为变更"，等用户单独确认。
4. **工作区干净**：开始前的改动都已提交或妥善暂存，重构 commit 不与未完成的半成品混在一起。

## 2. 常用重构手法

| 手法 | 适用 | 要点 |
|------|------|------|
| Extract（提取） | 重复块、超长函数中可命名的片段 | 提取函数/组件/模块；名字表达意图；两处重复先确认"会一起变"再提取 |
| Inline（内联） | 多余的间接层、只用一次的包装、补丁链遗留的中间函数 | 删掉间接层，调用点直接看到真实逻辑 |
| Rename（重命名） | 名字与行为不符、缩写、模糊名 | 最便宜收益最高的手法；改完靠编译/测试兜底 |
| Guard clauses（卫语句） | 深嵌套条件 | 提前 return 展平嵌套；注意不改变分支语义 |
| Parameterize（参数化） | 只差常量的相似函数 | 合并为一个带参数的函数；调用点全部更新后删旧函数 |
| Move（移动） | 职责错位的代码 | 业务逻辑移出 UI 层、工具逻辑移出组件；移动后检查依赖方向 |
| Immutability（不可变化） | 原地 mutate 且项目约定不可变 | 改为返回新对象；注意所有消费点都改用返回值 |
| Split（拆分） | 超长文件/上帝模块 | 按领域而非按技术类型拆分；拆出的文件各自内聚 |

**组合技**：一次只做一个手法，做完验证再做下一个。"提取 + 内联 + 重命名 + 参数化"混在一个 commit 里，出问题无法定位。

## 3. commit 策略

- **一个逻辑重构一个 commit**：消息用 `refactor(<scope>): <描述>`（遵循项目 CLAUDE.md 里的提交约定，有冲突以项目为准）
- **每个 commit 后跑验证**：测试/构建通过才继续下一个；失败就停在这一步修好再走
- **commit 消息说清动机**：不只写"提取了 validateEmail"，写"api.js 和 form.js 中重复的邮箱校验提取为共享工具，消除两处漂移风险"
- **cleanup 模式的 commit** 额外说明替换关系："用基于 X 的统一处理替换 3 个补丁提交中的特判分支（原 a1b2c3、d4e5f6）"
- 提交粒度以用户确认为准；用户没偏好时按上述默认

## 4. cleanup 模式：补丁链收敛

cleanup 模式的重构不是整理补丁，是**替换补丁链**：

1. 把补丁链要解决的问题逐一列成清单（来自 review 阶段的补丁痕迹检测）
2. 带着完整理解设计干净实现：如果没有历史包袱，这个问题应该一次解决成什么样？
3. 新实现完成后做**覆盖核对**：清单上每个症状都能指出"新代码中由哪里保证"
4. 删除全部废弃的补丁代码、特判、矛盾注释——收敛完成的标志是补丁链的痕迹清零
5. 用一个或少数几个 commit 完成替换；commit 消息写明替换了哪些补丁提交

## 5. 何时停手

- 剩余发现都是 P2，收益低于改动风险
- 某项重构会触及没有测试覆盖、且无法快速补验证的核心逻辑 → 不硬改，在报告的"不动的部分"里说明风险，交给用户决定
- 相关代码即将被重写/废弃（用户提到或从 roadmap 可见）
- 已经改到用户确认过的计划边界——新发现的问题记入报告遗留项，不擅自扩大范围
