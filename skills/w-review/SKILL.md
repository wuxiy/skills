# Review（方案评审 / 代码 review）

两件事共用一套纪律：**先钉死标准，再看实现，每条意见必须给证据，结论必须能落地**。

评审最容易失效的方式不是漏看，而是**看着顺眼就放过**——方案写得完整、代码跑得通，于是默认它成立。这个技能存在的意义是把"顺眼"换成"证据"。

## 与 w-code-refactor 的边界

| | w-review（本技能） | w-code-refactor |
|---|---|---|
| 动作 | **只读**，不改一行代码 | 审完动手重构 |
| 产出 | 评审结论 + 分级问题 + 证据 | 可运行的干净实现 |
| 时机 | 开工前（方案）/ 合并前（代码） | 写完之后收敛 |

用户只要意见就不要改代码。**除非明确说"顺手改掉"，否则一律只出报告。**

## 五条铁律

1. **只读**。不改文件、不提交、不"顺手修一下"。发现问题交回主编码 Agent 修——评审者和实现者分开，才避免自己给自己背书。
2. **无证据不入报告**。每条意见必须能指到位置（`文件:行` / 文档章节 / 命令输出）。指不到的证据，降级为「待确认问题」，不算缺陷。
3. **区分事实与推测**，并主动交代**什么证据会推翻自己的判断**。评审最怕的是把猜测说成结论。
4. **不得以「建议增强」打回**。禁止过度设计：不加抽象层、不做预留扩展、不为局部问题引入通用机制。评审意见只针对"这次需求要的东西是否正确实现"。
5. **结论必须可执行**。不许只输出"整体质量不错，建议关注"。必须落到三选一：**可以进** / **补齐后可进**（列出必须补的项）/ **不能进**（列出阻断原因）。

## 模式选择

| 模式 | 时机 | 典型输入 |
|------|------|----------|
| **plan** | 动工前 | Spec、ADR、实施计划、验收清单、PRD、技术方案讨论 |
| **code** | 合并前 | git diff、MR/PR、刚写完的实现、几轮修复后的收敛 |

自动识别：出现「方案 / 设计 / 计划 / 验收标准 / 要不要这么做 / 能不能开工」→ plan；出现「代码 / 实现 / diff / MR / PR / 提交前」→ code。两边都沾或都不沾，用用户输入工具问一次，不猜。

## 模式 A：方案评审（plan）

评审方案，本质是查**隐性假设有没有被暴露、取舍有没有被论证、不确定性有没有被先行验证**。

### 六维检查表

| # | 维度 | 问什么 | 不合格长什么样 |
|---|------|--------|----------------|
| 1 | **问题定义** | 问题能否复现？根因是什么？边界在哪？改什么、不改什么？ | 直接给解法，全程没说清要解决什么 |
| 2 | **隐性假设** | 并发边界？第三方挂了怎么降级？数据冲突/幂等？迁移与回滚？多端一致性？ | 这些一个都没提，全靠实现时临场拍 |
| 3 | **路径取舍** | 四条维度逐条给依据：实现复杂度 / 维护复杂度 / 时间与资源成本 / **可逆性** | 只有一个方案，且没说为什么不选另一个 |
| 4 | **不确定性是否先探** | 有风险的分支有没有 spike / 示踪弹（tracer bullet）先打通一条最小通路？ | 拿"应该可行"当可行性验证 |
| 5 | **验收标准可执行** | 每条可测量？未通过时是继续改还是登记阻塞？外部依赖阻塞如何绕过并留痕？ | "功能正常""体验良好"这类无法判定的表述 |
| 6 | **过度设计** | 奥卡姆：删掉这个抽象层/预留扩展，需求还成立吗？消融：拿掉某个组件，方案还闭环吗？ | 为"以后可能要"提前建框架 |

### 输出结构（plan）

```markdown
## 评审结论
[可以开工 / 补齐后可开工 / 不建议按当前方案做] + 一句话理由

## 必须补齐才能开工（BLOCKER）
1. <问题> — 证据：<文档章节/行> — 影响：<不补会怎样>

## 建议修改（MAJOR / MINOR）
...

## 方案里做对的地方
<明确指出，避免只列问题导致对方全盘推翻重来>

## 需要你回答的问题
<不超过 5 个，按对实现方向的影响排序；问完就能开工，不要穷尽细节>
```

### 尺度控制

问问题不是越多越好。当剩下的问题**已经不会显著改变实现方向和验收结果**时，就停止追问，判"可以开工"。把对齐本身做成重流程，是另一种失败。

## 模式 B：代码 review（code）

### 审查顺序（不要一上来逐行读 diff）

1. **先看验收标准，再看测试结果**。然后问一句关键的：**这些测试验证的，是这次需求真正关心的事吗？** 测试全绿但测的是无关紧要的路径，等于没测。
2. **沿业务路径看实现**，精力压在高风险区：**权限、状态变化、并发、重试、数据一致性、迁移与回滚**。模式稳定的 CRUD 少看甚至不看——那里花时间不产生发现。
3. **专门审新增的抽象和机制**。奥卡姆三问：真有必要吗？有没有更简单的实现？是不是为一个局部问题引入了通用复杂度？
4. **收敛复核**（多轮修复后必做）：探索过程留下的临时分支、兜底、重复逻辑、多余的 refresh/重载，是否已清理？保留的非显然约束，有没有写清 WHY 注释（字段语义 / 状态生命周期 / 时序边界）？

### 测试质量四条

- **测行为不测实现**——断言"用户能看到什么"，不是"内部调了哪个函数"
- **核心依赖禁 mock**——被 mock 掉的路径等于没验证
- **盯失败路径**——超时、重试、幂等、并发冲突、外部返回成功但实际没生效
- **规则写成 lint**——同一个错误被抓到两次，就该机械化了

### 输出结构（code）

```markdown
## 评审结论
[可以合并 / 修复后合并 / 不可合并] + 一句话理由

## BLOCKER（会导致线上事故 / 违反验收标准）
- `path/to/file.ts:42` — <问题> — 证据：<代码片段或命令输出> — 建议：<怎么改>

## MAJOR（潜在风险，非阻断）
## MINOR / NIT（可改可不改，明确标注"不阻断合并"）

## 本次不审的部分
<CRUD、样板代码、生成代码等，说明为什么跳过>

## 我不自信的点
<哪些结论缺证据、哪些场景没实测、哪些只是推测，以及什么证据能推翻它>
```

### MR 较小时的小技巧

改动小于一屏时，直接按上面顺序读；改动跨多个文件时，先用 `git diff --stat` 定位高风险文件，再只看这些文件的完整上下文（diff 会被截断，读全是必要的）。

## 反模式

- ❌ 只列问题不给证据 → 对方无法验证，也无法反驳
- ❌ 用"建议增加单元测试/建议补充文档"凑数 → 这不是发现
- ❌ 把可改可不改的 NIT 写成 BLOCKER → 阻断权和严重度不匹配，评审会失去公信力
- ❌ 评审者顺手改代码 → 实现和评审同源，等于没审
- ❌ 方案评审时替对方重新设计一遍 → 你要的是指出缺口，不是交付另一个方案
- ❌ 代码 review 时对"命名不够好"长篇大论，却漏了并发和回滚
