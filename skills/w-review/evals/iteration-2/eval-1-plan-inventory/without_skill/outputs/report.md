# 方案评审：支付成功扣库存

方向对，但现在开工会把最贵的坑写进代码。建议先补下面几条再动手。

## 必须改（P0）

1. **没有幂等**。支付回调几乎必然重投（微信/支付宝都会多次重试）。`qty = qty - 1` 不幂等，重放即多扣。必须落幂等键（callback_id 或 order_no）唯一约束，或靠订单状态机 `paid` 的单向流转拦住重复。

2. **会扣成负数**。这条 SQL 是无条件扣减，两笔支付并发时第二笔把库存打成 -1。改为 `... WHERE sku = ? AND qty >= 1`，用影响行数判定成败；失败要有显式分支（转异常单 + 告警 + 自动退款），不能静默。

3. **扣的是「1」不是「订单数量」**。回调应按订单行逐条扣，数量、SKU 取订单行的值。

4. **设计前提可疑**。「支付成功才扣库存」意味着商品页展示的库存没有被预占，多个用户可能都为最后一件付款成功，事后回滚。更稳的是下单预占（reserve）→ 支付确认（confirm）→ 超时释放。这条改动最贵，建议现在就定，别等上线后返工。

## 建议（P1）

- **`InventoryStrategy` 是过早抽象**。一个实现 + 一个「以后可能」，收益为零，成本是每次读代码多一跳。而且抽象轴选错了：第三方仓储的差异在可用量查询、预占/异步确认、超时补偿，不是一个 `deduct(sku, qty)` 能盖住的。先写一个诚实的 `InventoryService`，第二个实现真到了再抽，成本一样低。
- 补齐：回调验签与金额比对；退款/取消/超时的返还库存路径；扣减失败的告警与指标；库存展示缓存失效。

## 验收标准要重写

「功能正常，用户能正常下单」不可测，也没覆盖真正的风险面。换成可执行断言：

- 同一回调重放 5 次 → 库存只扣 1 次
- 库存 = 1，两笔支付并发 → 恰好一单成功，另一单进异常并有通知
- 库存不足 → 订单进异常态，库存不为负，有告警
- 已取消订单收到回调 → 不扣库存
