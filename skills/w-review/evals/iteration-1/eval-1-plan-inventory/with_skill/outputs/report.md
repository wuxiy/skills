# 方案评审：支付成功后扣库存

## 评审结论
**补齐后可开工** — 主链路选对了，但幂等与超卖两个正确性缺口没补，按现方案写出的代码会在第一次重复回调或并发回调时出错。

## 必须补齐才能开工（BLOCKER）

1. **回调不幂等，重复投递重复扣减** — 证据：原文「支付回调进来后直接 UPDATE inventory SET qty = qty - 1 WHERE sku = ?」，全文无幂等键/去重表/流水号/状态机。— 影响：支付回调均为至少一次投递，重试 N 次扣 N 件，直接资损。
2. **无超卖守卫与并发保护** — 证据：该 SQL 无 `AND qty >= 1`，无 version 乐观锁、无 FOR UPDATE。— 影响：qty 可扣成负数。
3. **支付成功但扣减失败无分支** — 证据：方案只有成功路径一句 UPDATE，未定义库存不足/DB 异常时的动作。— 影响：钱收了货没扣，静默不一致。
4. **验收标准不可判定** — 证据：原文「功能正常，用户能正常下单」。— 影响：无法判定扣减是否正确，也判定不出上述 3 条是否修好。建议改为：qty=N 回调一次→N-1；同一回调重放 3 次→仍 N-1；10 并发→qty≥0 且终值正确；扣减失败时订单状态可查。

## 建议修改（MAJOR）

1. **InventoryStrategy 属过度设计** — 证据：原文「为了以后扩展…以后要接第三方仓储直接加实现类」。— 影响：无第二实现、无第二份契约时只增维护成本，并把扣减语义锁死在一个为未知需求设计的接口上。奥卡姆自检：删掉接口需求依然成立。建议本次直写扣减逻辑，等第二个仓储真出现再抽。

## 方案里做对的地方
- 范围收得住，只做「支付成功→扣库存」，没扩到下单侧预占。
- 用单条原子 UPDATE 而非先 SELECT 再 UPDATE，方向正确，只差守卫条件与幂等层。
