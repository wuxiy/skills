# MR 评审：优化取消订单流程

**结论：不能合（Request changes）。** 描述与实际改动不符：这不是"流程优化"，而是去掉了后端的权限校验，并引入一个有状态的模块级缓存。

## 阻断项（P0）

**1. 垂直/水平越权 —— 任何人都能取消任意订单并触发退款**
`cancelOrder(id, userId)` 里 `userId` 完全没有被使用，`getOrder` 也不带归属判断。删掉前端 `canCancel` 后，等于把访问控制交给客户端——而客户端可以被绕过（直接调接口 / 改请求）。这是典型 IDOR，且能直接动用退款资金。必须后端校验订单归属（或角色），前端隐藏只作为 UX 手段。

**2. 缓存导致重复退款**
`cancelOrder` 先 `getOrder`（读到缓存里的旧对象）→ 退款 → 更新 DB，但**缓存从未失效**。同一订单第二次取消，`cache.has(id)` 命中旧数据，`status` 仍是 `PAID`，于是第二次调用退款接口。资金重复出账，是资损级缺陷。且 `Map` 永不清理 → 内存泄漏 + 多实例之间状态不一致。

**3. 退款与状态变更不在事务/不可重试**
先调退款再 `update`。若 update 失败 → 钱退了、单没取消；若退款成功后进程崩溃 → 重试再退一次。缺少幂等键、缺少状态前置校验（已 CANCELLED / REFUNDED / 已发货的订单仍可被取消）。

**4. 退款失败被静默吞掉**
`fetch` 未检查 `res.ok`、无 try/catch、无超时、无 Content-Type。非 2xx 时仍继续把状态改成 `CANCELLED`：用户没收到退款，订单显示已取消，账实不符。

## 建议修改（P1）
- `findUnique` 返回 `null` 时也 `cache.set`，下游 `order.status` 会抛 TypeError；缓存需区分未命中与空值、加 TTL，或干脆去掉这层（DB 有主键查询，收益存疑；若要有缓存，以 Redis + 显式失效为准）。
- 用状态机收敛：`PAID → CANCELLED` 才允许退款；取消操作做成幂等（唯一键 = orderId + 操作类型）。
- 内部支付接口需鉴权 + 超时 + 重试策略；退款结果落库（refundId）便于对账。
- 前端无条件渲染 `CancelButton` 后，用户会点到一个必然失败的按钮；即使后端补校验，也建议保留 disabled 态。
- 缺单测：至少覆盖"非本人订单"、"重复取消"、"退款失败"三条。

## 一句话
安全与资损问题各一处，改动量与风险远超"小改动"的描述，建议拆分：先补后端鉴权（必须），缓存这层建议本次直接移除。
