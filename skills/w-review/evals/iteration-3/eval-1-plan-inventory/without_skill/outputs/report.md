# 方案评审：支付成功后扣库存

**结论：不通过（需返工后开工）。** 核心机制（回调里直接 `UPDATE qty = qty - 1`）在真实支付回调语义下会重复扣减、可能扣成负数，且失败无补偿路径；验收标准无法验证。建议按 P0 修订后再排期。

---

## P0 — 阻断性问题（必须先解决）

### 1. 幂等性缺失：回调会重复扣减
支付渠道的回调/通知本质是 at-least-once，超时、网络抖动、我方处理慢都会触发重推；同一笔支付可能收到 N 次通知。方案中没有幂等键、去重记录或订单状态守卫，直接 `UPDATE ... qty = qty - 1` 意味着**收到几次扣几次**，库存被静默吃掉且无法自证。

必须补齐：
- 以支付流水号（或 `out_trade_no + 渠道通知 id`）为幂等键，落唯一索引，重复请求直接短路返回成功；
- 库存变动走 append-only 流水表（`inventory_ledger`：`sku, delta, 幂等键, 订单号, 时间`），`qty` 只作为快照/可由流水重算；
- 或订单状态机加前置守卫：`WHERE status = 'PAID_PENDING_DEDUCT'` 的条件更新，affected rows = 0 则视为已处理。

### 2. 可能扣成负库存
`SET qty = qty - 1 WHERE sku = ?` 是原子递减，但不含下界约束。并发场景下 10 个请求抢 3 件库存，会得到 `-7`。
- 改为 `UPDATE inventory SET qty = qty - 1 WHERE sku = ? AND qty >= 1`，并**检查 affected rows**，为 0 则走缺货分支；
- 多 SKU 订单在事务内**按 sku 排序**依次扣减，避免交叉死锁；
- 明确「扣不到库存」时订单怎么办：是回滚支付、转人工、还是挂超卖单发货？现在方案里没有这条路径。

### 3. 失败无补偿、无可见性
回调链路里同步扣库存，扣减失败（DB 抖动、缺货、死锁）时你怎么回渠道？返回失败让它重试 → 可能渠道已判成功；返回成功 → 库存没扣但钱收了。
- 建议：回调只做「验签 + 支付单置成功 + 写事件（本地消息表）」，库存扣减由消费者异步执行并重试，失败进死信 + 告警 + 人工补偿界面；
- 若坚持同步，至少要定义清楚失败返回值语义、重试次数与告警阈值。

## P1 — 影响可交付性

### 4. 验收标准不可测
「功能正常，用户能正常下单」无法作为验收项——它恰好覆盖不了本方案最可能出事的场景。替换为可执行断言：
- 同一支付通知重放 3 次，库存只减 1，流水只有 1 条；
- 库存 1 件、并发 100 单，成功 1 单、99 单收到明确缺货反馈，库存终值 = 0，无负值；
- 人为让扣减抛错，回调链路不丢单，事件进入重试并最终补偿成功（可查到记录）；
- 监控：扣减失败率、负库存告警、回调处理 p99 延迟。

### 5. 缺少回补/释放路径
退款、风控拦截、发货失败、超时未支付释放，都需要把库存加回去。方案里只有减，没有 `release/restore` 语义，之后一定会临时打补丁。接口契约里必须同时定义 `deduct / release / query` 三者及其幂等性。

## P2 — 建议调整

### 6. `InventoryStrategy` 是投机性抽象，且会藏住事务边界
现在只有一个实现、没有第二个已知接入方，"以后接第三方仓储"是假设而非需求。代价是：把事务边界切碎了——每个策略实现自己怎么开事务、怎么保证幂等和一致性，全靠实现者自觉，反而更难保证正确性。
- 建议本期不抽接口，先把扣减逻辑写成一处内聚的函数/仓储方法；
- 等真正出现第二个库存来源时，再按实际差异（同步 vs 异步、有无幂等键、有无批量）抽接口，那时才知道接口该长什么样。

### 7. 上线与灰度
存量在途订单、开关（可一键回退到人工扣减）、影子比对（新旧逻辑跑一遍比结果）、以及回滚后已扣库存的核对脚本——这些应该在开工前定下来，而不是上线当天想。

---

## 修订建议（最小改动集）
1. 幂等键 + 流水表 + 条件更新（`AND qty >= 1`）；
2. 回调与扣减解耦（事件 + 重试 + 死信告警），或明确同步失败的返回语义；
3. 补齐 release/restore 契约；
4. 验收标准改成上面 4 条可执行断言；
5. 砍掉 `InventoryStrategy` 抽象，留下一处内聚实现。
