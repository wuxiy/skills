# 方案评审：订单服务「支付成功后扣库存」

## 评审结论

**不建议按当前方案做** — 扣减语句缺少守卫条件与幂等保护，超卖和重复扣减是必然结果而非概率问题，而验收标准恰好无法发现这两件事。

## 必须补齐才能开工（BLOCKER）

1. **库存校验与扣减之间存在时序断裂** — 证据：方案原文「支付回调进来后直接 UPDATE … qty - 1」，全流程未提下单环节是否校验/预占库存 — 影响：若下单不预占，N 个并发订单可同时支付成功，最后一件商品被卖 N 次。这是设计缺口，不是实现细节。
2. **扣减语句无守卫条件** — 证据：`UPDATE inventory SET qty = qty - 1 WHERE sku = ?` 无 `AND qty >= 1`、无版本号 — 影响：库存为 1 时，两个并发事务都能更新成功，qty 变 -1。只差一个条件就能真正安全，现在不带。
3. **无幂等，回调重投会重复扣** — 证据：方案未提幂等键（out_trade_no 唯一约束 / 去重表）— 影响：支付回调是「至少一次」投递，网关重试、人工补单、消息重放都会多扣一次，且无法事后识别。
4. **无库存流水与对账留痕** — 证据：方案只有一条 UPDATE，无流水表、无回调原文留存 — 影响：账实不符时无法定位是哪笔单扣错，也无法与支付方账单按月核平。
5. **失败分支无归宿** — 证据：方案未定义「扣减失败（库存空/锁冲突/DB 超时）怎么办」— 影响：支付已成功而扣减失败，是退款、挂起还是补偿重试？没定义就会实现成吞异常，静默少扣。
6. **验收标准不可判定** — 证据：「功能正常，用户能正常下单」— 影响：第 1~3 条恰恰在「用户能正常下单」时同时发生。必须改成可测断言，例如：并发 10 单抢 1 件库存，成功 1 单、库存不为负；同一 out_trade_no 重投 3 次，库存只减 1。

## 建议修改（MAJOR / MINOR）

- **MAJOR｜退款、取消、超时未支付三种回补路径未覆盖** — 证据：方案全文无退款章节 — 影响：状态机缺「释放」态，退款后库存永久少 1。
- **MAJOR｜事务与回调响应边界未定** — 扣减与回 `success` 的先后、扣减失败时回什么，直接决定会不会触发自动重试，也直接决定第 3、5 条怎么修。
- **MINOR｜上线与回滚顺序未提** — 库存表已有数据或其他写入方时如何灰度、出问题如何停。
- **MINOR（不阻断）｜`InventoryStrategy` 属过度设计** — 证据：「为了以后扩展，先抽一层接口」。奥卡姆一问：删掉这层接口，本次需求仍然成立 → 成立。当前只有一个实现、一个调用点，加接口只多一层跳转和一份要长期维护的契约。等出现第二个真实实现再抽，成本更低。**这条不影响开工判定。**

## 方案里做对的地方

- 把动作放在**支付成功之后**而非下单即扣，方向正确：面向真实付款，避免大量无效占用。
- 用**单条 UPDATE 做增减**而不是「读-改-写」，已经避开了应用层竞态——只差一个守卫条件就能真正安全，改动成本极小。
- 改动范围明确锁在 `WHERE sku = ?`，没有顺手改别的表，边界清楚。

## 需要你回答的问题

1. 下单环节现在是否已校验/预占库存？作用域是「只校验不占用」还是「预占 N 分钟」？
2. 支付回调现在是否已有幂等去重？扣减是否与「回 success」在同一事务内？扣减失败回什么给支付方？
3. 扣减失败时你期望的行为：让支付方重试、进补偿队列，还是直接退款？
4. 本次范围是否包含退款/取消/超时未支付的库存回补？不包含就明说，登记为已知缺口。
5. 库存表现有历史数据吗？除本服务外还有谁写它（后台改库存、ERP 同步）？

## 我不自信的点

- 我没看到代码、表结构、支付回调实现。第 1、2 条的严重度依赖「下单侧是否已校验库存」与「回调是否已有幂等」，方案里都没写，我只能按「没写=没有」的保守假设判 BLOCKER。若你答已有，这两条应降级为「确认既有机制覆盖了本次新路径」。
- 未实测并发。超卖结论是从语句语义推断的，没有跑压测验证。
- 不知道库存表是否有 CHECK 约束或乐观锁字段，也不知道 `qty` 是有符号类型还是无符号。
- 能推翻上述判断的证据：下单流程中库存校验的代码位置、回调幂等键的定义、库存流水表结构。
