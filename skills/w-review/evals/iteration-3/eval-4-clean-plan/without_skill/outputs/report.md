# 评审：/api/reports 导出 CSV

**结论：方向认可，但有两个阻断项必须在开工前定，否则要返工。** 范围裁剪（同步、不分片、10000 上限）我同意，量级没到就别提前抽象。

## 阻断项

**B1. 「413」与「流式写响应」自相矛盾。**
要返回 413，就得在写出第一个字节之前知道行数；但「同步生成 + 流式写响应」是先查后写。实际流程只能是 `COUNT(*)` → 判断 → 再流式查询，同一谓词跑两遍。三个后果方案都没写：
- 两次查询之间数据会变（count=9999，实导出 10050），上限形同虚设 → 用 `LIMIT 10001` 兜底并按实际行数判定。
- COUNT 可能是最慢的一步（无索引筛选组合），5s 预算里它占多少？
- 若改成「边流边数、超了就断」，此时 200 已发出，无法再 413。**这两条路只能选一条，需要产品/前端一起定。**
- 顺带：413 语义是"请求体过大"，用在这里不准，建议 422 + 错误码。

**B2. 「复用 GET 鉴权」≠「复用 GET 的数据可见范围」。**
方案只交代了 403，没交代列表接口是否做行级/租户级过滤。若做了、而导出另起一条查询，最可能的线上事故就是**导出漏掉行级过滤、越权吐全量**。必须写明：导出调用列表接口同一个查询构造函数（含 where / sort / row-scope），不是"照它写一个"。验收加一条：受限账号导出 ⊆ 其在列表接口可见范围。

## 验收标准的缺口

- **验收 1/2 是同义反复**：查询构造有 bug 时两边一起错，测试照样绿。至少一条对照独立信源（固定种子数据集已知 N 行，或同谓词直连 DB count）。另外必须固定稳定排序键，否则分页列表与全量导出集合不可比。
- **「>10000 行」不可测**：没说怎么造数据。补 seed 脚本，或降级为单测 mock。
- **验收 4「不产生文件」测不到东西**：流式本来就不落盘。改成断言响应无 attachment / 无 CSV 字节。
- **验收 6 p95<5s 太虚**：开发机、没定义数据集形状（几列、字段多宽）、没讲冷热、p95 需多次采样。至少固定「10000 行 × 白名单全字段、预热后 20 次取 p95」，并单独报 COUNT 耗时。
- **验收 5「逐字段比对」**：必须写成遍历白名单的自动断言 + 单一共享常量，否则字段列表迟早漂移。

## 必须补进方案的实现细节

1. **CSV 注入**：`= + - @ TAB CR` 开头的单元格需前置 `'` 或转义，否则 Excel 打开即执行公式。用户可控字段一律处理。
2. **转义与编码**：逗号/引号/换行按 RFC4180 加引号；`\r\n`；UTF-8 **BOM**（不加则 Excel 中文乱码）；Content-Disposition 文件名带 `filename*=UTF-8''`。
3. **值语义**：null vs 空串、时间格式与时区。
4. **0 行结果**：只有表头的 CSV 还是 204？定一个。
5. **中断清理**：客户端断连要释放 cursor/连接；中途报错会产生半截文件，写明该行为。
6. **审计**：一万行用户数据的批量出口，建议记 who / 筛选指纹 / 行数 / 耗时 / 是否被 413 拦。成本极低，出事时是唯一溯源手段。
