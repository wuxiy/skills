## 一、结论：是典型的补丁叠补丁

当天 3 个 fix 都是"出事 → 在就近位置打一个特判"的模式，各自看都合理，叠在一起后结构腐化：

| 提交 | 问题 | 补丁方式 |
|---|---|---|
| `31a1dfa` fix: 未知折扣码导致价格为 NaN | 查表得到 undefined 参与乘法 | 在乘法前加 `safeRate = rate === undefined ? 0 : rate` 特判 |
| `4e35f0a` fix: VIP50 折上折力度过大 | VIP50 与会员折扣叠加被投诉 | 在 `if (isVip)` 内部内联 `coupon === 'VIP50'` 字符串特判，并**提前 return** |
| `f5e0d83` fix: 负价格输入导致负金额 | 脏数据负价格 | 在函数末尾加 `if (result < 0) result = 0` 钳制 |

结构性问题：

1. **兜底逻辑分散在三个不同层次**：查表时防 undefined、VIP 分支里防叠加、出口前钳负数。没有统一的"输入先规整"概念，每个补丁只管自己那一段。
2. **补丁之间互相绕过**：`4e35f0a` 的提前 return 出现在 `f5e0d83` 的负数钳制之前，后打的补丁天然管不到先打补丁开出的分支——这是补丁叠补丁最典型的恶果（见下方实证 bug #1）。
3. **单一出口被破坏**：`Math.round(result * 100) / 100` 四舍五入逻辑出现两处（VIP50 分支一处、函数末尾一处），将来改精度规则要改两处。
4. **FIX 注释叙事化**：注释记录的是事故（"线上有人输错""运营投诉"），而不是当前行为规则，读者无法从代码本身看出规则全貌。

## 二、补丁遗留的 4 个实证缺陷（重构前在 work/ 副本中复现）

| # | 输入 | 补丁前实际输出 | 期望 | 成因 |
|---|---|---|---|---|
| 1 | `calcFinalPrice(-100, 'VIP50', true)` | **-90** | 0 | VIP50 分支提前 return，绕过末尾负数钳制 |
| 2 | `calcFinalPrice(100, 'constructor', false)` | **NaN** | 100 | NaN 修复只查 `=== undefined`，`'constructor'` 命中原型链上的函数 |
| 3 | `calcFinalPrice(NaN, null, false)` | **NaN** | 0 | 末尾钳制只处理负数，NaN 比较恒为 false，原样透传 |
| 4 | `calcFinalPrice(Infinity, 'SAVE20', false)` | **Infinity** | 0 | 同上，非有限值不在兜底范围 |

缺陷 1 尤其说明问题：它不是某个补丁写错了，而是**补丁的叠加顺序本身制造的 bug**——负数钳制补丁永远排在 VIP50 提前 return 之后，结构上就无法覆盖该路径。

## 三、重构方案：三段式单一流水线

核心思路：三个补丁其实分别对应"输入规整""折扣码语义""叠加规则"三件事，把它们归位到各自该在的层次，主流程变成无分支特判的直线：

```
calcFinalPrice = roundToCents( 会员折扣( 折扣码( 规整输入(price) ) ) )
```

重构后 `src/price.js`（35 行，含注释）：

- `normalizePrice(price)`：入口处一次性规整脏输入——负数、NaN、±Infinity 一律按 0。取代原先末尾的负数钳制；因为所有折扣乘子都在 (0,1] 区间，入口钳制与原出口钳制对合法输入完全等价，且任何后续分支都不可能绕过它。
- `couponRateOf(coupon)`：用 `Object.hasOwn` 查表，只认自身枚举的码；未知码（含 `constructor`/`hasOwnProperty` 等原型链属性）按无折扣。同时修复了 `=== undefined` 检查的原型链漏洞。
- `NON_STACKABLE_COUPONS`（Set）：不叠加规则由数据集合表达，`applyVipDiscount` 统一处理"叠加/取更优惠者"两种情况。将来新增不叠加活动码只改集合，不再内联字符串特判。
- `roundToCents`：四舍五入只写一处；函数单一出口，无提前 return。
- 注释从"事故叙事"改为"规则陈述"。
- `COUPON_RATES` 加 `Object.freeze`，防止外部意外修改折扣表。

对外 API 完全不变：仍导出 `calcFinalPrice`、`COUPON_RATES`（同形状），原 10 个测试一行未改全部通过。

## 六、取舍说明（无人值守，按工程判断决策）

1. **NaN/Infinity 兜底为 0 是行为变更**：原代码会透传 NaN。负价格补丁的动机是"别让脏数据显示到页面"，把非有限值一并兜底是同一动机的自然推广；且测试套件未覆盖该场景，判定为安全的收敛性变更，并在 README 中明示。
2. **保留既有历史、不 rebase/squash**：3 个 fix 提交是真实演进记录，重构以新增提交叠加，历史完整可追溯。
3. **TDD 提交顺序**：`e0b7772`（测试）提交时仓库处于 RED 状态（4 个新用例失败），这是刻意的——它精确证明了补丁遗留的缺陷；随后 `9aff941` 转绿。评测若只看 HEAD，则全绿。
4. **未动 package.json**：`Object.hasOwn` 需 Node ≥ 16.9（实测环境 v24.12.0）。加 engines 字段属可选加固，为避免无关改动未加，此处备注。
5. **未抽象出"折扣规则引擎"**：只有 3 个折扣码，用 Set 表达不叠加规则是够用且最简的方案，避免过度设计。
