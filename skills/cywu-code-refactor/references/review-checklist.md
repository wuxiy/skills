## 1. 重复逻辑

**找什么：**

- 复制粘贴的代码块（约 5 行以上近乎相同）
- 只差常量/参数的相似函数（典型：两个 validate / 两个 format / 两个 fetch 包装）
- 重复的校验、错误处理、数据转换、默认值兜底逻辑
- 同一概念的两套并行实现（如两处各自维护同一份枚举/映射表）
- 跨文件重复：新功能复制了既有模块里已有的逻辑而没有复用

**判断原则：**

- 重复的两处**未来会一起变**→ 合并（提取函数/组件/工具模块）
- 重复的两处**只是现在恰好一样**、未来各自演化 → 强行合并反而是错误抽象，标注"暂不合并"并说明理由
- 宁可先标记"两次重复，观察第三次"，也不要为消灭重复造出别扭的抽象——错误的抽象比重复更难改

## 2. 设计问题

**找什么：**

- 超长函数（>50 行）、超长文件（项目有约定按约定，常见警戒线：典型 200-400 行，800 行是硬上限）
- 嵌套超过 4 层的条件/循环
- 上帝对象/上帝函数：一个模块同时管数据、请求、渲染、格式化等多重职责
- 职责错位：业务逻辑漏进 UI 层、数据获取混进纯计算、工具函数依赖全局状态
- 泄漏的抽象：调用方需要知道实现细节才能正确使用（如需手动调两次、顺序敏感）
- 命名与行为不符：函数名叫 `getX` 却有副作用；`handleClick` 里做了 200 行数据加工
- 违反项目既有约定（如项目要求不可变模式，新代码却在原地 mutate 对象）
- 死代码：没人调用的函数、注释掉的代码块、永远进不去的分支

**判断原则：**

- 优先修"改起来便宜、收益立竿见影"的：rename、guard clause 降嵌套、提取函数
- 涉及模块边界调整的改动先评估波及面（谁调用它？改接口要动几处？），波及面大的单独列为一个计划项
- 死代码直接删，版本控制会记得它——留着只会误导下一个读代码的人

## 3. UI 一致性

仅适用于包含 UI 的项目；纯后端/CLI 项目跳过此维度并在报告注明。

**找什么：**

- 同一语义的控件多种实现：确认按钮有 3 种样式、错误提示有的用 toast 有的用行内红字
- 魔法值：颜色、间距、字号、圆角用了裸数值，而项目已有 design token / 主题变量 / 样式常量
- 状态处理不一致：有的列表有 loading/empty/error 三态，同类列表只有 empty
- 交互模式漂移：表单提交有的防抖有的不防抖、关闭弹窗有的二次确认有的不确认
- 新写的组件与项目既有组件库重复造轮子（先确认项目里真的没有，再看是不是封装不够好导致别人不知道有）

**判断原则：**

- 以**项目现有模式**为基准做对齐，不是引入新的设计规范
- 分不清是"该对齐"还是"本来就该不同"时（比如主按钮和危险按钮的差异），列出疑点问用户，不擅自统一
- 纯视觉微调（1px 级别）归入 P2，不进 P0/P1

## 4. 性能

**找什么：**

- 循环内的重复全量查找/过滤导致的 O(n²) 及以上
- N+1：循环里发请求/查库（应改批量）
- 无谓重算：每次调用都重算可以缓存/记忆化的结果；渲染路径里做昂贵计算
- 前端特有：不必要的重渲染（缺 memo/依赖数组错误）、大体积依赖、未处理尺寸的图片、无虚拟化的长列表
- 无界增长：只进不出的缓存/数组/监听器（内存泄漏隐患）
- 大结果集无分页/截断

**判断原则：**

- 性能结论要证据：指出具体代码位置 + 复杂度分析或可观察的现象（"列表 1000 项时该循环执行约 100 万次比较"），不写"可能有点慢"
- 只动热路径和可证明的瓶颈；冷代码的微优化是 P2
- 以性能为名的重构若会牺牲可读性，在报告里写明权衡，让用户选

## 5. 补丁痕迹检测（仅 cleanup 模式）

先还原历史：按顺序读最近几轮修复的提交（`git log` + 逐个 `git show`），回答三个问题——每个补丁修的是什么症状？当时为什么选择这种修法？根因到底是什么？

**找什么：**

- **叠层修补**：后一个提交在前一个提交的 workaround 上再加条件/特判
- **特判代码**：`if (specialCase)`、硬编码的例外值、绕过问题的 flag
- **吞错止血**：用 try-catch 吞异常、用默认值掩盖上游数据问题
- **残留物**：补丁链中被后续提交废弃但没删的代码、与现状矛盾的注释、调试遗留
- **症状修复 vs 根因修复**：判断每个补丁修的是症状还是根因；连续修症状通常意味着根因没找到

**判断原则：**

- 收敛的目标不是"把补丁整理好看"，而是**从需求出发重新推导一次干净的实现**：如果带着今天对问题的完整理解重写这段代码，它应该长什么样？
- 重写方案必须覆盖补丁链修过的所有症状——逐个列出"原补丁 X 解决的问题，新方案中由 Y 保证"
- 若根因仍不确定（补丁有效但说不清为什么有效），停下来告诉用户，不要在没搞懂机制的情况下重写——那只会造出下一个补丁
